# Local links for 0.0.x development

[한국어](local-links.ko.md)

## Status and scope

The owner decided this on 2026-10-15 and it is in effect. It covers every development checkout of the polyspec repositories and of consumer, the folders `polyspec/` and `consumer/` beside each other in one workspace folder, while the polyspec versions are 0.0.x.

## Decision

Development is completed against the latest source of each polyspec repository, with no release in between.

- An installed polyspec package is linked to the source of the repository that provides it, and the link counts as the installed released version.
- Releases follow in one batch after development is complete, in dependency order: kit → ordered-json → orm, template → crudui → hyper → fsm, template-benchmark.
- Builds, CI and the batch release use released versions. A link exists only in a local checkout and is never committed.

Why: development stalled because each repository waited for another repository's release, which waited for a third. With every package linked to its source, a change is visible at once in every consumer.

## Mechanism

The links are the kit tool `scripts/kit/link.mts` (K201, K201-1, K205), which uses the simplest mechanism that each ecosystem allows. Only a package pinned at 0.0.x is linked: the version comes from each tool's own record (npm query, Composer's `installed.json`, `uv pip list`, the requirement of `go mod edit -json`), and any other pin is reported `NOT linked (pinned <version>, not 0.0.x)` and fails.

| Ecosystem | Link |
|---|---|
| npm | Each copy that `npm query` lists below `node_modules` of an npm project of the consumer is replaced by a symbolic link to the provider's package folder; a copy that `npm query` does not list is linked only when it already is that link, else it is reported `NOT linked (not recorded by npm query: <folder>)`, never at a guessed version. |
| Composer | The vendor of each Composer project of the consumer is the one that `composer config vendor-dir` gives it (also one that `COMPOSER_VENDOR_DIR` places); each copy that its `composer/installed.json` lists at its `install-path` is replaced by a symbolic link to the provider's package folder, and `composer dump-autoload` runs once in each such project on every `link` run (not `check`), linked or not. A vendor without `installed.json` is reported `NOT linked (not installed in <vendor>)`; a record without `install-path` is `NOT linked`; each `polyspec/*` name of `require` or `require-dev` in the consumer's `composer.json` files without a linked record is reported `NOT linked` too. |
| Python | Each declared polyspec package, each polyspec package below it and each project of the environment (the consumer's own and each workspace member, polyspec or not, by its `[project]` name) is installed from its editable wheel (K222, K224), per environment, with no sync (K239): the consumer's install has already synced the environment, and a sync of the lock would reinstall any other package from its lock source, so the link runs none; every wheel is resolved before the install, so a missing one leaves the environment untouched; then `uv pip install --reinstall-package <name> --constraints <file>` with the wheels of the linked providers, without `--no-deps`, so the dependencies of each checkout are installed, and a second `uv pip install --no-deps --reinstall-package <name>` with the wheels of the projects of the environment, whose dependencies the consumer's lock sync provides (K280); the file is `uv export --frozen --all-groups --no-emit-workspace` of the lock without the linked packages, so every locked version holds (K237). A wheel that is missing is built only where its package folder is writable (K224: the folder, not the checkout), through the backend of the checkout's `pyproject.toml` `[build-system]`, in an isolated env: `uv run --no-project --isolated --with <requires> python -c` calls its `build_editable`. A read-only folder with no wheel of its fingerprint is reported `NOT linked (stale prebuilt wheel <name> (fingerprint <fp>): run kit link on the host)` and fails. The state comes from `uv pip list --format json` (the pin, the presence) and `uv pip freeze` (the `name @ file:` of the wheel, PEP 610). The requirements are read as PEP 508 and PEP 735 define them. The environment is `VENV`, else uv's project environment (`UV_PROJECT_ENVIRONMENT`, else `.venv`) of the workspace root that `uv workspace dir` prints. |
| Go | Each Go module of the consumer gets a git-ignored `go.work` at its root, with `use` lines for the module and the provider modules; go reads it by itself, so no variable is set. `kit.mk` sets `GOWORK=off` for the release targets and `dependency-review`, which use the released versions. `unlink` removes the files. |
| Rust | `link.mjs cargo <dir> <cargo args>` runs one cargo command with `--config` `[patch]` entries for the URL that each provider declares in `config/release.json` and a `resolver.lockfile-path` to a copy of the tracked lock under `var/link/cargo`, made afresh on every run; nothing is written globally. |

- Python editable wheels (K222): the fingerprint of a provider is the first 12 hex of sha256 over the resolved absolute path of its checkout, its `pyproject.toml` bytes and the sorted directories below it, without those that a build writes. The path is part of it because an editable wheel is bound to the path it points at: a wheel built for one checkout is never reused for another, while the host and the container mount the same path and share one wheel (hidden, `build`, `dist`, `__pycache__`, `*.egg-info`). The wheel is kept in `var/link/wheels/<name>/<fingerprint>/`, a git-ignored folder of the consumer; the fingerprint is a folder and not part of the file name, because a wheel file name must be a valid PEP 427 name (a build tag starts with a digit, and `name-<hex>.whl` has no Python tag, which uv rejects). `check` fails when the installed wheel has another fingerprint than the checkout now has. Reason: setuptools' PEP 660 build writes `<name>.egg-info` into the source tree and calls `os.utime` on it, and a test container mounts the polyspec checkouts read-only and writes as uid 295 against directories owned by 501 with mode 755, so an editable `-e` install that builds inside the container fails with EACCES. The wheel is built where the checkout is writable (the host), and the container only installs it. The `-e` lines and the `--overrides` file are gone. Each project of the environment is one more package of this kind (K224): its fingerprint is over its own folder, its wheel is `var/link/wheels/<its name>/<fingerprint>/`, and `check` verifies its installed wheel like a provider's. The sync does not build it, since `uv sync` without `--no-install-project` built it in place and failed on a read-only consumer for the same `os.utime` reason. unlink leaves the built wheels, which are caches.
- Declaration: the checkouts are arguments, not a variable. `link` and `check` take the main checkout of each polyspec repository that provides packages (`kit link <checkout>...`), and `--project <dir>` names the consumer, else the whole tree of the working directory. Without checkouts nothing is linked and the installs stay the locked releases. No variable selects a mode: a build or a check is the same whether linked or not.
- Providers: each tracked manifest of a package in a main checkout that the arguments name provides (`package.json` `name` of a package, private or not, since "private" stops publishing and not linking; `composer.json` `name`, `pyproject.toml` `project.name`, `go.mod` `module`). A linked worktree is never a provider, and a package of the consumer's own repository, identified by its common Git directory, is never linked, also from a worktree of it. Two package folders that provide one name fail with both, and so do two repository roots of different checkouts; a repository root next to a package folder is the development project and yields. Tests, examples, benchmarks, documents, config/, .mise and fixtures provide nothing and are never linked; release-consumer projects are tests.
- No copies: a provider is never copied. Each polyspec folder of a `node_modules` or a vendor that the tool's record does not list is a plain copy and is reported `NOT linked` with its path; a package installed from a `file:` tarball is linked like any other install.
- No builds: `link` only links. A provider is built by `link.mjs rebuild <repository>...` or its own target, with the targets of its own Makefile that its release builds (the prerequisites of `release-assets`; a missing prerequisite fails with make's error), else `build`. A linked npm provider is STALE while an output that its `package.json` names is missing, or an input is newer than the oldest output and the inputs differ from the digest recorded after its last rebuild (`var/link/built/` of the provider); `check` fails on it.
- Writes: each file that the tool writes into a repository (`var/link` of a consumer, `var/link/built` of a provider, the `go.work` and `go.work.sum` of each Go module of a consumer, the Cargo lock copy) and each link that replaces an installed folder is one that Git ignores there (`git check-ignore`), so a consumer must ignore `var/link`, `go.work` and `go.work.sum`. A folder is outside Git only when no `.git` entry (a directory or a gitfile, even a broken one) exists in it or above it; inside a repository, every failure of git fails with git's own message (K201-3). A path that Git does not ignore fails with its name; no shared folder outside the consumer takes its files (K205 removed the fallback of K203).
- Commands, in a kit checkout: `make link CHECKOUTS="<checkout>..."`, `make link-check CHECKOUTS="..."` and `make unlink`, each with `PROJECT=<dir>` to name the consumer (else the whole tree of the checkout). `make install-packages` never builds or links (K205): after an install, run `make link` again, and confirm with `make link-check`.
- `--project` (S-426): `link`, `check` and `unlink` with `--project` handle only the manifests directly in each `<dir>` (package.json, composer.json, pyproject.toml, go.mod), never a nested project. Without it, the whole tree under `<dir>` is handled. The install recipe of `kit-bootstrap.mk` passes it, so an install links exactly the project it installed. A named project that is not installed still fails. With `--project`, the Composer project is `<dir>` itself: its vendor is the one that `composer config vendor-dir` gives in `<dir>`; a `<dir>` without a composer.json involves no Composer, and no vendor above `<dir>` is ever taken (K201-3).
- Repository variables: a Git hook exports the variables of its own repository (GIT_DIR, GIT_INDEX_FILE, ...), so every git command and make that `link` runs in another repository, such as a provider checkout, runs without the variables that `git rev-parse --local-env-vars` lists, as git does for a submodule (K201-4).
- Commands elsewhere, such as consumer, which has no kit: `node <kit checkout>/dist/link.mjs link|check [--project <dir>] <checkout>...`, `unlink [--project <dir>]`, `rebuild <repository>...`, `packages <dir> python|npm` (the declared polyspec packages, one per line) and `cargo [--checkout <checkout>]... <dir> <cargo args>`. The tools are `NPM`, `COMPOSER_BIN`, `UV`, `GO` and `CARGO` when a recipe gives them, else the tools of the consumer (`var/tools/bin/npm`, the shims of mise, the Composer of `mise.toml`, the cargo of rustup); a missing tool fails with its cause. The kit checkout is built once (`make build` in it).
- A recipe that installs from its lock runs `link` right after the install, in the same recipe: for example a `$(PYTHON)` rule whose `uv sync --frozen` runs on every make. A check of the environment against the lock, such as `uv sync --frozen --check`, takes the polyspec packages out and checks the third-party packages exactly: `uv sync --frozen --check --inexact` with `--no-install-package <name>` for each name that `link.mjs packages <dir> python` prints. The links are checked by `link.mjs check`.
- `check` lists every installed copy and every declared polyspec dependency as linked, NOT linked, STALE or own (this repository); NOT linked and STALE fail it.
- `unlink` restores each checkout with each tool's own install (`npm ci`, `composer install` in the project after the links are removed, `uv sync --locked`), removes the files that link wrote for the consumer (`go.work`, `go.work.sum` and the Cargo lock copies; the built Python wheels under `var/link/wheels` stay) and then each folder that is left empty, never a folder recursively, so the files of a nested consumer stay; it reports each restore that it skips, which fails it.

## Known effects

- `npm ci`, `composer install` and `uv sync` remove the links; run `link` again after an install, and confirm with `link-check`. `make install-packages` does not link (K205).
- The package manager still records the released version (lock files, Composer's `installed.json`). A check that compares installed packages with their lock fails while linked; it is run after unlinking or after the batch release.
- npm resolves a linked package's own dependencies from the provider checkout's `node_modules`; Composer resolves them from the consumer's vendor, so a provider's new Composer requirement must also be installed in the consumer.
- A PHP C extension is not linked; it needs a built shared library.
- A dependency pinned to a version the provider no longer has (ssr's ordered-json `=0.0.2`) is not linkable and is moved in the integration pass.

## Ownership

The session `link-owner` owns the links and keeps the registry `polyspec/scratch/link/REGISTRY.md`: each session, its folders and their link state. Other sessions run the link on their own folders and report `link.mjs check` to it.

## End

After development is complete, every checkout is unlinked, every repository takes its dependencies at the new releases once, and this document is closed.

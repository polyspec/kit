# Local links for 0.0.x development

[한국어](local-links.ko.md)

## Status and scope

The owner decided this on 2026-10-15 and it is in effect. It covers every development checkout of the polyspec repositories and of consumer, the folders `polyspec/` and `consumer/` beside each other in one workspace folder, while the polyspec versions are 0.0.x.

## Decision

Development is completed against the latest source of each polyspec repository. Nothing is released until development of all of them is complete: no tag, no version bump and no release workflow run in any repository, kit included. A push is a backup and publishes nothing; a change to kit is seen in the other checkouts through the links after `make build`.

- An installed polyspec package is linked to the source of the repository that provides it, and the link counts as the installed released version.
- Releases follow in one batch after development is complete, in dependency order: kit → ordered-json → orm, template → crudui → hyper → fsm, template-benchmark.
- Builds use the links to the sibling checkouts. Nothing waits for a release, because a tracked file locks no 0.0.x polyspec package (Tracked locks). A link exists only in a local checkout and is never committed.

Why: development stalled because each repository waited for another repository's release, which waited for a third. With every package linked to its source, a change is visible at once in every consumer.

## Tracked locks (K468)

A tracked file reads the same in every checkout, so a tracked lock describes only the packages that the repository itself declares. A tracked lock never describes a polyspec package of 0.0.x, and no item waits for a release because of one.

- A tracked manifest or lock names no polyspec package of 0.0.x: no Composer `require`, `require-dev` or `packages` entry, no npm dependency section or `packages` node, no pyproject dependency or pylock package, and no source of one (a URL, a git repository, a tag, a path, a file or a relative folder). `make polyspec-lock-check` fails on each such entry, by file and name.
- The declarations live in `config/polyspec.json` (schema `scripts/kit/schema/polyspec.schema.json`): for each ecosystem, the project folder, named from the repository root, and the names of the packages that it consumes, and the repository that provides them as `owner/name` (K473). A declaration holds no version, URL or path, since the provider is the sibling checkout.
- link installs each declared package from the sibling checkout that provides it, as a link. The installed folder is the link and counts as the released version. A declared package that no checkout provides fails the link and names it (`NOT linked <ecosystem> <name> (no provider)`); nothing is downloaded in its place. The link manifest requires a declared Composer package as `*` at the version that its provider's composer.json declares, and npm links a declared package that is not installed as a symbolic link in the project's node_modules.
- A tracked lock covers the third-party packages only. Its consistency with the tracked manifest is checked by the tool of its ecosystem (`npm ci`, `composer validate --check-lock`, `uv lock --check`).
- The link files (`composer.link.json`, the temporary npm manifest and the uv overrides) carry the declared requirements of the linked install. The tracked files never carry them.

Why this model, attacked:

- A lock of sibling content (a path or a git source generated from a sibling checkout) changes with each sibling commit, so it churns and does not reproduce on another machine; it needs a relative path, an absolute path or a git revision, which the rules of this repository forbid for 0.0.x.
- Keeping a release entry and re-resolving it locally consumes a release, which is forbidden. It also fails when the release requires a newer PHP than the policy: orm 0.0.18 requires php >=8.5 against the policy 8.4.1.
- Keeping the requirement in the manifest and dropping only its lock entry leaves the tracked state inconsistent: `npm ci` and `composer validate --check-lock` reject it.
- Waiting for a batch release is an indefinite deferral (P36).

Accepted costs:

- A checkout without its sibling checkouts, such as a fresh clone, cannot run the code that imports a declared package. The link names the missing checkout and stops. This is the 0.0.x model: development runs against the sibling sources.
- CI of a repository that declares a package needs its sibling checkouts. The workflows are vendored from kit, so the CI change is made in kit and copied by `make kit-sync`. The vendored gates workflow clones each declared `repository` beside the project at its default branch, before install, and runs `make link` before the gates (K473); the project lies in the folder named by its repository, so the clones lie beside it, as link reads them.

Publishing later:

- At the batch release, in dependency order, the release step moves each declared package into the manifest at its released version, re-resolves the tracked lock from the registry, which records the integrity of the release, and removes the declaration. The result is a function of the manifests and the registry at that release, so a fresh checkout reproduces it. No tracked state waits for that step before it.

Enforced by: `make polyspec-lock-check`.

## Verification

`make link-state-check` (K305-1, P30) is a gate of every repository. It compares no version and no requirement, since the link counts as the installed released version and versions are checked at install only. While a link exists it fails, naming the ecosystem and the package, when an installed polyspec package pinned at 0.0.x is a plain copy among links, when a link resolves to no package of that name (npm `package.json`, Composer `composer.json`), when a Composer package is a link over the install of a release archive (its record in `installed.json` does not say `dist` type `path`), or when a `go.work` `use` folder has no `go.mod`. A checkout without a link passes, so CI, which installs the released packages, is unaffected. The pre-push gate keeps refusing a link record. While a Composer project is linked (its `composer.link.lock` exists), `make dependency-policy-check` judges every Composer rule of that project (the platform, the locked requirements of the tracked lock, `composer validate` and the review versions) on `composer.link.json` and `composer.link.lock` (K326-2), fails a polyspec package of a path repository that the link lock holds from another dist, and leaves the review hash of the tracked `composer.lock` to the check of the batch release (K326). Composer reads `repositories` only from the root manifest, so the same check fails a root `composer.json` that requires a polyspec package whose `composer.json` declares a repository (such as a fork) that the root lacks, naming both, and the link writes the repositories of each linked package into `composer.link.json` (K330). A linked package (a path dist of the link lock, a symbolic link of `node_modules`) is not compared with the latest release of the registry, in `make dependency-review` and in the policy check; a third-party package still is (K328).

## Mechanism

The links are the kit tool `scripts/kit/link.mts` (K201, K201-1, K205), which uses the simplest mechanism that each ecosystem allows. Only a package pinned at 0.0.x is linked: the version comes from each tool's own record (npm query, Composer's `installed.json`, `uv pip list`, the requirement of `go mod edit -json`), and any other pin is reported `NOT linked (pinned <version>, not 0.0.x)` and fails.

| Ecosystem | Link |
|---|---|
| npm | Each copy that `npm query` lists below `node_modules` of an npm project of the consumer is replaced by a symbolic link to the provider's package folder; a copy that `npm query` does not list is linked only when it already is that link, else it is reported `NOT linked (not recorded by npm query: <folder>)`, never at a guessed version. |
| Composer | The vendor of each Composer project of the consumer is the one that `composer config vendor-dir` gives it (also one that `COMPOSER_VENDOR_DIR` places). Composer installs the linked packages itself (K304-1): link writes a git-ignored `composer.link.json` (a copy of the tracked `composer.json` with a path repository `{ "type": "path", "url": <provider folder>, "options": { "symlink": true, "versions": { <name>: <locked release> } } }` for each linked package in front of the repositories, so the folder takes precedence over the archive of the release) and `composer.link.lock` (written from `composer.lock` only when it is missing, and kept afterwards, so what `UPDATE` applied to it survives a relink; K392), keeps both out of Git through `.git/info/exclude`, and runs `COMPOSER=composer.link.json composer update <the linked polyspec packages and the path packages of the project> --with-dependencies --no-scripts --no-plugins` (K331). Only those packages are resolved, from their folders; every other package stays at its locked release; the installed folder of each is a symbolic link; and `installed.json`, the autoload rules and the platform check Composer writes come from the `composer.json` of the folder, so Composer checks the versions of the folder at that install. The tracked `composer.json` and `composer.lock` are never changed. `unlink` removes the two link files and runs `composer install`. A vendor without `installed.json` is reported `NOT linked (not installed in <vendor>)`; a record without `install-path` is `NOT linked`; each `polyspec/*` name of `require` or `require-dev` in the consumer's `composer.json` files without a linked record is reported `NOT linked` too. |
| Python | Each declared polyspec package and each polyspec package below it is installed from an editable wheel that link writes into `var/link/python` (K398), per environment, with no sync (K239): the consumer's install has already synced the environment, and a sync of the lock would reinstall any other package from its lock source, so the link runs none. `uv pip install --reinstall-package <name> --constraints <file> --overrides <file> <wheel>` installs the wheel of each linked provider, without `--no-deps`, so the dependencies of each checkout are installed at the locked releases, and uv writes the console scripts and checks `Requires-Python` at that install. Each project of the environment, the consumer's own and each workspace member (K224), polyspec or not, by its `[project]` name, is installed from its editable wheel in the same way, with `--no-deps` (K280), since the consumer's lock sync provides its dependencies: link writes nothing into its folder, so a read-only project is linked (K398-1). The wheel is written by link and no build backend runs: its METADATA is the `[project]` table of the provider's `pyproject.toml` (name, version, `Requires-Python`, one `Requires-Dist` per dependency), its entry points are `[project.scripts]`, and its one `.pth` names the import root, which is the `package-dir` of `""`, else `src` of the folder when it exists, else the folder. Link refuses a provider or a project whose metadata a build backend computes, with `NOT linked` and the reason: a dynamic `version`, `dependencies` or `requires-python`, a `package-dir` of other than `""`, or a backend that compiles code (maturin, scikit-build-core, meson-python, setuptools `ext-modules`). There is no fallback to `uv pip install -e` for such a provider or project. After each install link writes the PEP 610 `direct_url.json` of the distribution as `{"url": "file://<folder>", "dir_info": {"editable": true}}`, the record of an editable install of the folder, so the state below is read as before. The constraints file is `uv export --frozen --all-groups --no-emit-workspace` of the lock without the linked packages, so every locked version holds (K237); the overrides file names each linked provider by its wheel, so a package that requires another linked one by its release URL does not conflict, and names each project by its wheel too. A declared polyspec package that the environment lacks (the install recipe's sync leaves out the polyspec packages and removes the editables of an earlier link) is installed the same way, at the version of its folder, so the link is idempotent (K316-2). The state comes from the environment itself (PEP 610 `direct_url.json`: the folder and `dir_info.editable`) and `uv pip check`. The requirements are read as PEP 508 and PEP 735 define them. The environment is `VENV`, else uv's project environment (`UV_PROJECT_ENVIRONMENT`, else `.venv`) of the workspace root that `uv workspace dir` prints. |
| Go | Each Go module of the consumer gets a git-ignored `go.work` at its root, with `use` lines for the module and the provider modules; go reads it by itself, so no variable is set. `kit.mk` sets `GOWORK=off` for the release targets and `dependency-review`, which use the released versions. `unlink` removes the files. |
| Rust | `link.mjs cargo <dir> <cargo args>` runs one cargo command with `--config` `[patch]` entries for the URL that each provider declares in `config/release.json` and a `resolver.lockfile-path` to a copy of the tracked lock under `var/link/cargo`, made afresh on every run; nothing is written globally. |

A consumer installs its Composer projects with `make composer-install DIR=<project>` in place of `composer install`. When a sibling checkout provides a polyspec package that the `composer.lock` of the project holds, it writes `composer.link.json` and `composer.link.lock` as link does and runs the partial update from them, so each provided package resolves from its folder and the released metadata of the lock is never read; without such a sibling, as in CI, it runs `composer install` of the tracked lock, and it prints which of the two it took (K432). A vendor without `installed.json`, as in a fresh checkout, names the polyspec packages of its `composer.lock` in `make link-check`, which reports them NOT linked until the install has run.

- Declaration: the checkouts are arguments, not a variable. `link` and `check` take the main checkout of each polyspec repository that provides packages (`kit link <checkout>...`), and `--project <dir>` names the consumer, else the whole tree of the working directory. Without checkouts nothing is linked and the installs stay the locked releases. No variable selects a mode: a build or a check is the same whether linked or not.
- Providers: each tracked manifest of a package in a main checkout that the arguments name provides (`package.json` `name` of a package, private or not, since "private" stops publishing and not linking; `composer.json` `name`, `pyproject.toml` `project.name`, `go.mod` `module`). A linked worktree is never a provider of another repository, and a package of the consumer's own repository, identified by its common Git directory, is never linked, also from a worktree of it: the work tree that runs the link, a main checkout or a worktree, provides the packages of its own repository as own, and a checkout of that repository among the arguments provides nothing, so a worktree never takes the sources of its main checkout and names no checkout of its own (K385). Two package folders that provide one name fail with both, and so do two repository roots of different checkouts; a repository root next to a package folder is the development project and yields. Tests, examples, benchmarks, documents, config/, .mise and fixtures provide nothing and are never linked; release-consumer projects are tests.
- Forks (K379): each subfolder of `forks/` in the workspace folder, beside the polyspec checkouts (`forks/json-schema` beside `polyspec/kit`), that is a main checkout (a `.git` directory with a `HEAD`) is a provider, and `link --siblings` takes it with the main checkouts. The folder name is not the package name, and the origin is not checked: a fork's origin is its own repository and may be any URL, so `forks/json-schema` provides the package that its manifest names (for example `opis/json-schema`, from its `composer.json` `name`), read with the same manifests as any provider. A fork is linked like any other provider, and the consumer's pin is not changed: the link keeps the version that the consumer's install records, which the install checks, the 0.0.x pin rule above does not apply to a fork, because a fork's pin is a version of the fork (such as 2.6.0-p1), which the install records and checks.
- Consumer vcs repositories (K475): a `vcs` repository of a Composer consumer's `composer.json` resolves offline through the sibling checkout whose `origin` names the same repository (https or ssh, with or without `.git`), as a path repository of that checkout, so the provider entries of its `composer.lock` are written with no network. A vcs repository that no sibling checkout names fails, naming it; it is never skipped.
- No copies: a provider is never copied. Each polyspec folder of a `node_modules` or a vendor that the tool's record does not list is a plain copy and is reported `NOT linked` with its path; a package installed from a `file:` tarball is linked like any other install.
- Python wheels (K398): link writes nothing into a provider or project folder, which may be read-only. A provider's wheel holds only metadata derived from its `pyproject.toml` and a `.pth` naming its folder (or its `src`), so every import reads the folder itself. That does not break the rule of K316 that nothing is copied: the wheel holds no source, and its metadata is the information that an editable install keeps outside the folder anyway (in its `*.dist-info`). When that `pyproject.toml` changes, the metadata goes stale as the metadata of any editable install does, and link writes a new wheel at its next install of that provider.
- No builds: `link` only links. A provider is built by `link.mjs rebuild <repository>...` or its own target, with the targets of its own Makefile that its release builds (the prerequisites of `release-assets`; a missing prerequisite fails with make's error), else `build`. A linked npm provider is STALE while an output that its `package.json` names is missing, or an input is newer than the oldest output and the inputs differ from the digest recorded after its last rebuild (`var/link/built/` of the provider); `check` fails on it.
- Writes: each file that the tool writes into a repository (`var/link` of a consumer, `var/link/built` of a provider, the `go.work` and `go.work.sum` of each Go module of a consumer, the Cargo lock copy) and each link that replaces an installed folder is one that Git ignores there (`git check-ignore`), so a consumer must ignore `var/link`, `go.work` and `go.work.sum`. A folder is outside Git only when no `.git` entry (a directory or a gitfile, even a broken one) exists in it or above it; inside a repository, every failure of git fails with git's own message (K201-3). A path that Git does not ignore fails with its name; no shared folder outside the consumer takes its files (K205 removed the fallback of K203).
- Commands, in a kit checkout: `make link CHECKOUTS="<checkout>..."`, `make link-check CHECKOUTS="..."` and `make unlink`, each with `PROJECT=<dir>` to name the consumer (else the whole tree of the checkout). `make install-packages` only installs (K205, K360-1), and `make install` links last, with `make install-link` after the tools and the steps of the repository, whose environments the link reads (K360-2); after another install, run `make link` again, and confirm with `make link-check`.
- `--project` (S-426): `link`, `check` and `unlink` with `--project` handle only the manifests directly in each `<dir>` (package.json, composer.json, pyproject.toml, go.mod), never a nested project. Without it, the whole tree under `<dir>` is handled. The install recipe of `kit-bootstrap.mk` passes it, so an install links exactly the project it installed. A named project that is not installed still fails. With `--project`, the Composer project is `<dir>` itself: its vendor is the one that `composer config vendor-dir` gives in `<dir>`; a `<dir>` without a composer.json involves no Composer, and no vendor above `<dir>` is ever taken (K201-3).
- Repository variables: a Git hook exports the variables of its own repository (GIT_DIR, GIT_INDEX_FILE, ...), so every git command and make that `link` runs in another repository, such as a provider checkout, runs without the variables that `git rev-parse --local-env-vars` lists, as git does for a submodule (K201-4).
- Commands elsewhere, such as consumer, which has no kit: `node <kit checkout>/dist/link.mjs link|check [--project <dir>] <checkout>...`, `unlink [--project <dir>]`, `rebuild <repository>...`, `packages <dir> python|npm` (the declared polyspec packages, one per line), `providers <checkout>...` (the npm providers of the checkouts, a name, a tab and the package folder per line, read by the rules of link, K462) and `cargo [--siblings] [--checkout <checkout>]... <dir> <cargo args>`; `--siblings` takes the checkouts beside the project, and `make cargo-fetch DIR=<project>` is `cargo --siblings <dir> fetch --locked` (K448-5). The tools are `NPM`, `COMPOSER_BIN`, `UV`, `GO` and `CARGO` when a recipe gives them, else the tools of the consumer (`var/tools/bin/npm`, the shims of mise, the Composer of `mise.toml`, the cargo of rustup); a missing tool fails with its cause. The kit checkout is built once (`make build` in it).
- A recipe that installs from its lock runs `link` right after the install, in the same recipe, where a link can link and outside the install chain (K349-2): the rule holds for an ecosystem in which the repository declares a polyspec dependency (kit declares none), and a recipe that `make install` reaches, through a prerequisite or a `$(MAKE)` call, is covered by the one final `install-link` of `install` (K360-2); a recipe outside that chain, such as a generator that reinstalls from a lock, links right after itself. For example: for example a `$(PYTHON)` rule whose `uv sync --frozen` runs on every make. A check of the environment against the lock, such as `uv sync --frozen --check`, takes the polyspec packages out and checks the third-party packages exactly: `uv sync --frozen --check --inexact` with `--no-install-package <name>` for each name that `link.mjs packages <dir> python` prints. The links are checked by `link.mjs check`.
- `check` lists every installed copy and every declared polyspec dependency as linked, NOT linked, STALE or own (this repository); NOT linked and STALE fail it.
- `unlink` restores each checkout with each tool's own install (`npm ci`, `composer install` in the project after the links are removed, `uv sync --locked`), removes the files that link wrote for the consumer (`go.work`, `go.work.sum` and the Cargo lock copies, `composer.link.json` and `composer.link.lock`) and then each folder that is left empty, never a folder recursively, so the files of a nested consumer stay; it reports each restore that it skips, which fails it.

## Worktrees

- A row that needs a worktree gets it from `make worktree-setup NAME=<name> ID=<id> [TYPE=<type>]` in the main checkout (K348): the worktree `../<repository>-<name>-<id>` on the branch `<type>/<name>-<id>` from `main` (P10), installed from its own sources with `make install` (the tools and the packages, the steps of the repository, then the links) and checked with `make link-state-check`. A second run on the same worktree installs and checks it again, so a run leaves the same state.
- In a checkout beside the kit checkout `../kit`, the bootstrap takes `../kit/dist` as `KIT` from the first make on, the provider that the link installs, so a fresh worktree reads `kit.mk` before `npm ci` and installs with the tools of the kit it develops against; a kit checkout that is not built fails with `make build in ../kit` (K348-1). Without it, as in CI, `KIT` is the installed package.
- No worktree is made while the free disk is under 30 GB (`WORKTREE_DISK_FLOOR` of `scripts/kit/worktree-setup.mts`).
- An install directory of a worktree (`node_modules`, `vendor`, `.venv`, `target`, `var`) is its own, never a symbolic link to another checkout, so its tests run its own sources (K375). The tools of mise are no such install: a worktree reads the installs of mise of the main checkout of its repository (`MISE_SHARED_INSTALL_DIRS`), so it installs only the tools that the main checkout lacks, while its data dir, state, shims and wrappers stay its own (K387).
- `main` may be written directly by one actor per checkout, through gated commits (P38). Every commit on `main` runs the gates that `make land` selects for its staged paths, through the pre-commit hook that `make hooks` writes, and is refused only on a finding that `HEAD` lacks, which it names. A merge commit on `main` is refused by the pre-merge-commit hook, so `main` moves by commits and fast-forwards only. Parallel or isolated work uses a worktree and a branch (above) and reaches `main` by `make land`, which removes the worktree and the branch right after the merge. The first commit of a repository, which creates `main`, has no commit to compare with and is not gated. The hooks protect against an accidental ungated commit; a deliberate bypass (`--no-verify`, `core.hooksPath`, a raw `update-ref`) is out of scope.
- A worktree and its branch are removed as soon as the branch is merged into `main`: `make land` removes the branch that it lands, and `make worktree-prune` removes every branch whose own commits (those after the creation point that its reflog records) are all in `main`, with its worktree when that has no uncommitted change; a fresh branch, with no commit of its own, is kept. `make link-state-check` fails while a merged branch is left (K381).

## Known effects

- `npm ci`, `composer install` and `uv sync` remove the links; run `link` again after an install, and confirm with `link-check`. `make install` links the installed packages to the polyspec checkouts beside the repository when there are any, as its last step `make install-link`, after the tools and the steps of the repository (`link --siblings`, K349, K360-1, K360-2), with the link of the kit checkout beside it when there is one (K360); `make link` and `make link-check` without `CHECKOUTS` take those checkouts too, also in a worktree (K383); a recipe that installs from a lock without the link step after it fails `make link-state-check`, as does a linked vendor whose platform check demands a newer PHP than `.php-version` (K384).
- The package manager still records the released version (lock files, Composer's `installed.json`). A check that compares installed packages with their lock fails while linked; it is run after unlinking or after the batch release.
- npm resolves a linked package's own dependencies from the provider checkout's `node_modules`; Composer resolves them from the consumer's vendor, so a provider's new Composer requirement must also be installed in the consumer.
- A PHP C extension is not linked; it needs a built shared library.
- A dependency pinned to a version the provider no longer has (ssr's ordered-json `=0.0.2`) is not linkable and is moved in the integration pass.

## Ownership

The session `link-owner` owns the links and keeps the registry `polyspec/scratch/link/REGISTRY.md`: each session, its folders and their link state. Other sessions run the link on their own folders and report `link.mjs check` to it.

## End

After development is complete, every checkout is unlinked, every repository takes its dependencies at the new releases once, and this document is closed.
